Every Meetly API request must include an API key in the `Authorization` header. Meetly supports Bearer token authentication — you obtain an API key from your dashboard and pass it with every request. There are no session cookies or OAuth flows required for server-to-server integrations.

## Header Format

Include your API key in the `Authorization` header using the `Bearer` scheme:

```
Authorization: Bearer YOUR_API_KEY
```

The examples below show how to add this header in the most common environments.

<CodeGroup>

```bash curl
curl --request GET \
  --url https://api.meetly.ai/v1/meetings \
  --header "Authorization: Bearer YOUR_API_KEY"
```

```python Python
import httpx

client = httpx.Client(
    base_url="https://api.meetly.ai/v1",
    headers={"Authorization": "Bearer YOUR_API_KEY"},
)

response = client.get("/meetings")
print(response.json())
```

```javascript JavaScript
const response = await fetch("https://api.meetly.ai/v1/meetings", {
  method: "GET",
  headers: {
    Authorization: "Bearer YOUR_API_KEY",
  },
});

const data = await response.json();
console.log(data);
```

</CodeGroup>

<Warning>
  Never embed your API key in client-side code or commit it to version control.
  Use environment variables or a secrets manager to keep your keys secure.
</Warning>

## Key Types

Meetly issues two categories of API key, distinguished by their prefix. You can find and manage both types in the **API Keys** section of your dashboard.

<ParamField path="mk_live_*" type="Production key">
  Operations performed with a production key affect real data — meetings are
  created, transcriptions are processed, and usage counts against your plan
  quota. Use these keys only in production environments.
</ParamField>

<ParamField path="mk_test_*" type="Test key">
  Operations performed with a test key run in a sandboxed environment. No real
  data is created or modified, and no usage is billed. Use these keys during
  development and in your CI/CD pipelines.
</ParamField>

<Tip>
  You can tell which key type is active at a glance by checking the prefix:
  `mk_live_` for production and `mk_test_` for test.
</Tip>

## Authentication Errors

Meetly returns one of two HTTP error codes when authentication fails. Understanding the difference helps you diagnose problems quickly.

### 401 Unauthorized

A `401` response means the `Authorization` header is missing, the key is malformed, or the key has been revoked. Check that you are including the header and that the key value is correct.

```json
{
  "error": {
    "code": "authentication_failed",
    "message": "API key missing or invalid. Provide a valid Bearer token in the Authorization header.",
    "details": {}
  }
}
```

Common causes:
- The `Authorization` header is absent from the request.
- The key string contains extra whitespace or is truncated.
- The key has been revoked from the dashboard.

### 403 Forbidden

A `403` response means your key is valid and recognized, but it does not have the required scope to perform the requested operation. Review the permissions assigned to the key in your dashboard.

```json
{
  "error": {
    "code": "forbidden",
    "message": "Your API key does not have permission to perform this action.",
    "details": {
      "required_scope": "meetings:write"
    }
  }
}
```

<Note>
  If you need additional scopes, generate a new key with the required
  permissions rather than modifying an existing key that is already in use.
</Note>

## Rotating Your API Key

You should rotate your API key if it is compromised, if a team member with access leaves your organization, or as part of a routine security policy. Follow these steps to rotate without downtime:

1. **Create a new key** — In your Meetly dashboard, navigate to **Settings → API Keys** and generate a new key with the same scopes as the key you are replacing.
2. **Update your integration** — Replace the old key value with the new one in all environments (production, staging, CI). Verify that your application is using the new key by checking your request logs.
3. **Revoke the old key** — Once you have confirmed the new key is working correctly, return to **Settings → API Keys** and revoke the old key. Revocation is immediate and irreversible.

<Warning>
  Revoking a key before updating your integration will cause all requests using
  that key to fail with a `401` error. Always update your integration first.
</Warning>
